## The request log migration (manual, same day)

The proof above starts on an empty database. To see what 1.7.0 does to a database 1.6.0 has run on, the proof ran on v1.6.0 with `--keep` (18 rows in `request_logs`), then:

1. **1.7.0 on that database** started in about 4 s and logged `request log database schema is ready elapsed=11ms`. `_agentgateway_request_log_migrations` gained version 2 (`add request log analytics columns`) and 3 (`backfill request log analytics columns`): five nullable columns on `request_logs` (`cache_read_input_tokens`, `cache_creation_input_tokens`, `reasoning_tokens`, `time_to_first_token_ms`, `time_per_output_token_ms`), filled from the existing rows. Nothing else in the schema changed.
2. **1.6.0 on the migrated database does not start**: `failed to migrate request log database schema … migration 2 was previously applied but is missing in the resolved migrations`, exit 1. Reverting the image alone would crash-loop the gateway.
3. **Rollback:** after `DELETE FROM _agentgateway_request_log_migrations WHERE version IN (2, 3)` 1.6.0 started and answered 200; the extra columns do not bother it.
4. **Upgrading again** after that rollback: 1.7.0 started, re-recorded versions 2 and 3 over the existing columns, and answered 200.
