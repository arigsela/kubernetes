# Base Applications Directory

This directory contains Argo CD Application manifests and their corresponding
Kubernetes resources. The `master-app` Application (`master-app.yaml`, which
manages itself) discovers and deploys every top-level `.yaml` file in this
directory. It does not recurse, so subdirectories are only reached via the
Application that points at them.

Twelve apps that need no per-app Argo CD configuration are instead generated by
the `managed-apps` ApplicationSet (`managed-apps.yaml`) from configs in
`appsets/managed-apps/` — see `docs/managed-apps-appset.md`.

**What's deployed:** [`index.md`](index.md) lists every app directory with its
description, namespace, and links to its `docs.md` / `runbook.md`. It is
generated by `scripts/gen-okf.py`, so it stays current; don't hand-edit it.

## Directory Structure

Each application follows this structure:
```
base-apps/
├── app-name.yaml              # Argo CD Application manifest
└── app-name/                  # Kubernetes resources
    ├── deployments.yaml
    ├── services.yaml
    ├── configmaps.yaml
    ├── httproute.yaml         # Route on the shared Istio Gateway
    ├── certificate.yaml       # TLS Certificate for the host (letsencrypt-route53)
    ├── reference-grant.yaml   # Lets the Gateway read the certificate Secret
    ├── secret-store.yaml      # Vault SecretStore config
    ├── external-secret.yaml   # ExternalSecret resources
    ├── docs.md, runbook.md    # Agent-docs contract (in-scope apps)
    ├── catalog-info.yaml      # Backstage entity (never applied; excluded below)
    ├── mkdocs.yml, docs/      # Generated TechDocs mirror (scripts/gen-techdocs.py)
    └── crossplane_resources.yaml  # Crossplane managed resources, if any
```

## Adding a New Application

The Backstage **New Application** template (`templates/new-app/`) scaffolds all
of this as a PR. By hand:

1. Create the application directory and add its manifests:
   ```bash
   mkdir -p base-apps/my-app
   ```
   - **No `imagePullSecrets` needed** for ECR images — the native
     `inject-ecr-pull-secret` MutatingAdmissionPolicy adds them.

2. Create the Argo CD Application:
   ```bash
   cat > base-apps/my-app.yaml << EOF
   apiVersion: argoproj.io/v1alpha1
   kind: Application
   metadata:
     name: my-app
     namespace: argo-cd
     finalizers:
       - resources-finalizer.argocd.argoproj.io
   spec:
     project: default
     source:
       repoURL: https://github.com/arigsela/kubernetes
       targetRevision: main
       path: base-apps/my-app
       directory:
         exclude: '{catalog-info.yaml,mkdocs.yml}'
     destination:
       server: https://kubernetes.default.svc
       namespace: my-app
     syncPolicy:
       automated:
         prune: true
         selfHeal: true
       syncOptions:
         - CreateNamespace=true
   EOF
   ```

3. If the app has a public host: add an `HTTPRoute` (see below), a `Certificate`
   and `ReferenceGrant`, a listener on the Gateway and an allow-list rule in
   `istio-ingress/`, and the hostname to `wan-ip-monitor`'s managed list. See
   `istio-ingress/runbook.md` ("Adding a host").

4. Onboard it to the agent-docs contract (`templates/agent-docs/README.md`).

5. Open a PR. After merge, Argo CD deploys it.

## Disabling an Application

To disable an application without deleting its manifests:
```bash
git mv base-apps/app-name.yaml base-apps/app-name.yaml.disabled
```

Argo CD prunes the Application. Hand-written Applications carry the
`resources-finalizer`, so the app's resources are deleted with it.
(`master-app` and the ApplicationSet-generated Applications carry none.)

## Secret Management

Applications use Vault for secret storage with External Secrets Operator for synchronization:

1. **SecretStore** - Configures the Vault connection for the namespace
2. **ExternalSecret** - Maps Vault secrets to Kubernetes secrets
3. **Refresh Interval** - Usually `1h`

Most apps use a Vault role named after the namespace. Agent and database
credentials get their own ServiceAccount, SecretStore and Vault role
(`templates/agent-identity/README.md`).

Example:
```yaml
# secret-store.yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: vault-backend
  namespace: my-app
spec:
  provider:
    vault:
      server: "http://vault.vault.svc.cluster.local:8200"
      path: "k8s-secrets"
      version: "v2"
      auth:
        kubernetes:
          mountPath: "kubernetes"
          role: "my-app"

---
# external-secret.yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: my-app-secrets
  namespace: my-app
spec:
  refreshInterval: "1h"
  secretStoreRef:
    name: vault-backend
  target:
    name: my-app-secrets
  data:
  - secretKey: api-key
    remoteRef:
      key: my-app
      property: api-key
```

## ECR Authentication

ECR image pull authentication is fully automated by a CronJob and a native admission policy:

```
Every 15 minutes      ──▶ CronJob writes a fresh ecr-registry secret into every namespace
                          (a new namespace has it within 15 min)
Pod with ECR Image    ──▶ API server (native MutatingAdmissionPolicy) adds imagePullSecrets
```

**No manual steps required.** When deploying a new application that pulls from ECR:
1. Create your deployment manifests (no `imagePullSecrets` needed)
2. Create the Argo CD Application with `CreateNamespace=true`
3. A brand-new namespace gets `ecr-registry` within 15 minutes (pods retry
   the pull until then); to have it at once:
   `kubectl create job -n kube-system --from=cronjob/ecr-credentials-sync ecr-sync-now`

### How It Works
- **`inject-ecr-pull-secret`** (native MutatingAdmissionPolicy in `admission-policies`, no webhook) — Mutates pods that reference `.dkr.ecr.` images (containers, initContainers or image volumes) to add `imagePullSecrets: [{name: ecr-registry}]`
- **`ecr-credentials-sync`** (CronJob, `base-apps/ecr-auth/`) — Every 15 minutes, writes a fresh ECR token as `ecr-registry` into every non-system namespace via dynamic discovery, new namespaces included (ECR tokens last 12h)

## Ingress

Every public host is an `HTTPRoute` attached to a listener on the shared `main`
Gateway in `istio-ingress`. Access is default-deny by source IP through the
`AuthorizationPolicy` in `istio-ingress/authorizationpolicy.yaml`, and the Coraza
WAF (`istio-waf/`) runs on the same gateway. More specific path matches win, so a
backend can take `/api` while the frontend takes `/`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
spec:
  parentRefs:
    - name: main
      namespace: istio-ingress
      sectionName: https-my-app
  hostnames: [my-app.arigsela.com]
  rules:
    - matches:
        - path: {type: PathPrefix, value: /api}
      backendRefs:
        - name: my-app-backend
          port: 8000
```

The Istio ambient dataplane (`istio-cni`, `istio-ztunnel`) is installed, but no
namespace is enrolled in the mesh today.

## Admission Policies and Kyverno

Policies are native `ValidatingAdmissionPolicy` / `MutatingAdmissionPolicy` objects in
`admission-policies/`, tested against a real API server (`tests/admission-policies/`).
New policies start in shadow (`[Warn, Audit]`, `failurePolicy: Ignore`), move to `[Deny]` +
`failurePolicy: Fail` once proven, and opt in to PolicyReports with the label
`reports.kyverno.io/enabled: "true"`. See `admission-policies/runbook.md`
("Add or change a policy").

Kyverno (Helm chart 3.9.1) has no policies left; it only produces PolicyReports:
```bash
kubectl get policyreports -A
kubectl get clusterpolicyreports
```

## Terraform (Atlantis)

Atlantis (`atlantis.yaml` here, `atlantis/`) plans every PR that touches `.tf`
files. Apply happens **while the PR is open** — comment `atlantis apply` or run
the "Terraform Apply (gated)" Action — and the PR merges only after
`atlantis/apply` is green. See `atlantis/docs.md` and the header of
`terraform/roots/asela-cluster/argocd.tf`.

## Troubleshooting

### Application Not Deploying
1. Check Argo CD application status: `kubectl get applications -n argo-cd`
2. Check whether the root app is suspended by `scripts/argo-sync-window.sh`
3. Check Argo CD logs for sync errors; see `argo-cd/runbook.md`

### Secrets Not Syncing
1. Verify ExternalSecret status: `kubectl get externalsecret -n namespace`
2. Check SecretStore connection: `kubectl describe secretstore -n namespace`
3. Validate the Vault path, role, and the role's bound ServiceAccount

### ECR Pull Failures
1. Check if the ecr-registry secret exists: `kubectl get secret ecr-registry -n namespace`
2. Verify imagePullSecrets were injected: `kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.imagePullSecrets}'`
   (the MutatingAdmissionPolicy has `failurePolicy: Ignore`, so a failure there is silent)
3. Check ECR CronJob status: `kubectl get cronjob -n kube-system ecr-credentials-sync`
4. Manually trigger token refresh: `kubectl create job --from=cronjob/ecr-credentials-sync ecr-manual -n kube-system`
