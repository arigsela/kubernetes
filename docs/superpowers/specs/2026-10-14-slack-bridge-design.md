# Slack bridge: talk to a kagent agent from Slack, approve from Slack, as one verified principal

**Date:** 2026-10-14. **Follows:** `2026-10-14-restart-approvals-page-design.md` (§T.119),
`2026-10-13-callers-as-principals-and-eval-gate-design.md` (§V.91, §V.92).

## Goal

The owner asks a kagent agent a question from Slack (a mention in a channel or a DM) and reads
the answer in the thread; a follow-up in the same thread continues the same session. When an
agent pauses on a gated tool, or when the dispatcher posts a "Restart awaiting approval"
message, the owner decides it with an Approve or Reject button in Slack, and the decision is
recorded with the owner's email, as the approvals page records it today.

Today the only ways to an agent are `scripts/ask-hk` on a laptop with the repo and a kubelogin
token, and the kagent UI (one shared identity, and blind to dispatcher-owned sessions).
Approving a restart needs the approvals page or the CLI.

**Decisions taken in the design conversation (2026-10-14):**
- Only the owner may talk to the bridge: one allow-listed Slack user id. Anyone else gets an
  ephemeral "not for you" and nothing is sent anywhere.
- Every agent is reachable, including `restarter` and `implementer`, and approvals happen in
  Slack. The owner heard the risk (a second thing that can approve a pod delete) and chose it.
- The bridge is the Slack app n8n already posts with (Socket Mode and Interactivity enabled on
  it, plus an app-level token), so buttons on n8n-posted messages reach the bridge.
- Approach B: the bridge is its own app with its own identity, not a dispatcher sidecar, so a
  Slack chat is attributed to `system:serviceaccount:slack-bridge:slack-bridge`, never to the
  dispatcher.
- Packaging: stdlib Python in a generated ConfigMap, the dispatcher pattern. The Socket Mode
  websocket client is written in the stdlib and tested against a fake server.

**Out of scope:** slash commands; per-user identity (Slack user → Dex email); a persistent
thread→session map (the thread's first reply carries the session id for `ask-hk`); a reject
reason typed in Slack (a reject carries the fixed reason `rejected in Slack`); rate limits
beyond one connection and one replica; anything in Slack beyond text and two buttons.

## Design

### 1. The app (`base-apps/slack-bridge/`)

A new Argo CD Application `slack-bridge` (directory exclude for `catalog-info.yaml,mkdocs.yml`,
as every agent-docs app). Namespace `slack-bridge`, label `istio.io/dataplane-mode: ambient`
(its calls reach the controller through the kagent waypoint, §V.91).

- `serviceaccount.yaml`: `slack-bridge` (`automountServiceAccountToken: false`; the pod's only
  token is the projected one below) and `eso-slack-bridge` (the SecretStore's identity).
- `deployment.yaml`: one replica, `Recreate`, `python:3.12-slim`, command
  `python -u /opt/slack-bridge/slack_bridge.py`, the code ConfigMap at `/opt/slack-bridge`,
  a projected token (audience `kagent`, 1 h) at `/var/run/kagent/token`, the same security
  context as the dispatcher. Env: `OWNER_SLACK_USER_ID`, `OWNER_EMAIL` (what the dispatcher
  logs as approver), `DEFAULT_AGENT=homelab-knowledge`, `AGENTS` (comma list; the allow-list
  of agent names the first word may pick), `KAGENT_A2A_BASE`, `DISPATCHER_DECIDE_BASE=
  http://dispatcher.dispatcher.svc.cluster.local:8082`, `A2A_TIMEOUT=300`, `PORT=8080`
  (health only), and `SLACK_BOT_TOKEN` / `SLACK_APP_TOKEN` from the Secret `slack-bridge`.
  Annotation `checksum/code` (the generator writes it; the manifest test checks it).
- `code-configmap.yaml`: GENERATED by `scripts/gen-slack-bridge-configmap.py` from
  `scripts/slack_bridge.py` and `scripts/kagent_a2a.py` (imported unchanged). CI runs `--check`.
- `secret-store.yaml` + `external-secret.yaml`: SecretStore `vault-slack-bridge` (role
  `slack-bridge`, SA `eso-slack-bridge`), ExternalSecret `slack-bridge` → Secret `slack-bridge`
  with `bot-token` and `app-token` from Vault key `k8s-secrets/slack-bridge`. The bot token is a
  COPY of the one under `k8s-secrets/n8n`: one consumer, one path (agent-identity invariant 1).
- `scripts/provision-slack-bridge-vault.sh`: idempotent; writes the two tokens (read from
  stdin prompts, never printed), policy `slack-bridge` (read `k8s-secrets/data/slack-bridge`),
  kubernetes-auth role `slack-bridge` bound to `eso-slack-bridge` in `slack-bridge`, ttl 1h.
  Run BEFORE the manifests merge (a SecretStore whose role does not exist fails the app sync).
- No NetworkPolicy and no Service of its own: nothing calls the bridge (the health port is
  for the kubelet's probes). Egress is not restricted (Slack is outbound HTTPS, as n8n's).
- `base-apps/kagent/network-policy-controller.yaml`: admit namespace `slack-bridge`.
- `docs.md`, `runbook.md`, `catalog-info.yaml`; `scripts/agent-docs-scope.txt` gains the app;
  `gen-techdocs` and `gen-okf` are re-run.

### 2. Slack side (owner action, once)

On the Slack app n8n posts with: enable Socket Mode (creates the app-level token, scope
`connections:write`); enable Interactivity (no request URL is needed in Socket Mode); subscribe
to bot events `app_mention`, `message.channels`, `message.im`; add bot scopes `app_mentions:read`,
`channels:history`, `im:history`, `chat:write`, `reactions:write`; enable the Messages tab in
App Home so DMs work; reinstall. Invite the bot to `#oncall-alerts` (it already is, it posts
there). Signing-secret verification does not apply to Socket Mode (the envelope arrives on a
socket the bridge opened with the app token).

### 3. The code (`scripts/slack_bridge.py`, stdlib)

Three units behind small interfaces, so each is tested alone:

**`WebSocket` + `SocketMode`.** `WebSocket.connect(url)` does the RFC 6455 client handshake
(`ssl` for `wss://`, plain for `ws://` so the tests can run a fake server), `send_text`,
`recv()` → `(opcode, bytes)`, masks client frames, answers ping with pong, raises on close.
`SocketMode.run(on_envelope)`: `POST apps.connections.open` (app token) → `wss` URL; connect;
loop over JSON messages: `hello` (log), `disconnect` (reconnect at once: Slack asks every few
hours), `events_api` / `interactive` envelopes → hand the envelope to a worker thread, then
send the ack `{"envelope_id": …}` once the worker has queued it. On any socket error: reconnect
with backoff 1, 2, 4 … 60 s. One connection, one replica.

**`Slack` (Web API).** `post_message(channel, text, *, thread_ts=None, blocks=None)`,
`post_ephemeral(channel, user, text)`, `react(channel, ts, name, add=True)`,
`update_message(channel, ts, text, blocks)`. urllib, bot token, `ok: false` → `SlackError`.
Messages longer than 3 900 characters are cut with "… (truncated)".

**`Bridge`.** State: `threads: dict[thread_key, Thread(agent, context_id)]` and
`pending: dict[ctx, Pending(task_id, calls, nonce)]`, both in memory, both under a lock.
- `handle_event(event)`: ignore `bot_id`, `subtype`, and events from any user but
  `OWNER_SLACK_USER_ID` (those get an ephemeral refusal, logged `event: refused`). Accept a DM,
  an `app_mention`, or a channel message whose `thread_ts` is a thread the bridge knows (no
  mention needed inside a known thread). Strip the `<@bot>` mention. `agent, text =
  pick_agent(text)`: a first word `name:` that is in `AGENTS` picks the agent for the whole
  thread; otherwise `DEFAULT_AGENT`; an unknown `name:` is not an agent pick (it is text).
  `thread_key = thread_ts or ts`. React 👀, send over A2A (`a2a.send_message` with the HITL
  extension, context id from the thread if known, token from the file on every send), then:
  - completed → post the answer in the thread; the FIRST reply of a thread ends with
    `_session <ctx> · continue: scripts/ask-hk --agent kagent/<agent> --as-serviceaccount
    slack-bridge/slack-bridge --context <ctx>_`.
  - waiting with pending calls → register `Pending`, post the calls (`name` + JSON args, one
    per line, in a code block) with Approve / Reject buttons whose value is `s:<ctx>:<nonce>`.
  - waiting with a question → post the question; the next reply in the thread is sent as an
    `ask_user_response` (the bridge remembers the request id in `Thread`).
  - failed / error / timeout → post the error and the session id (if any) in the thread.
  Remove 👀, add ✅ or ❌. Every outcome is one JSON log line (`event: ask`, with
  `agent`, `session`, `state`, `error`, `user`).
- `handle_action(payload)`: `block_actions` only; the clicker must be the owner (ephemeral
  refusal otherwise, logged). `action_id` ∈ {`approve`, `reject`}; the value's prefix routes:
  - `d:<ctx>:<nonce>` → `POST <DISPATCHER_DECIDE_BASE>/decide/<ctx>/<approve|reject>` with JSON
    `{nonce, reason, approver: OWNER_EMAIL}`; the dispatcher's answer text is posted in the
    thread (202: "sent; the outcome lands here"; 404: "the dispatcher no longer holds it: use
    the ask-hk fallback in the message above"; 409: "already decided").
  - `s:<ctx>:<nonce>` → claim the bridge's own `Pending` (nonce must match; a second click gets
    "already decided"), send `tool_approval_response` for exactly the registered call ids on
    the registered task, under the bridge's token; post the agent's answer, or a NEW pending
    block if it paused again (never auto-approved).
  After either, `update_message` replaces the buttons with "Approved by <email> via Slack" /
  "Rejected …", so a stale message cannot be clicked twice. Log `event: decision`.
- Health: `/healthz` always 200; `/readyz` 200 once the socket has said `hello` and 503 after
  it dropped (the Deployment's readiness probe; nothing routes to the pod, it is for `kubectl`).

### 4. The dispatcher's third door (`scripts/dispatch.py`)

A third `ThreadingHTTPServer` on `0.0.0.0:DECIDE_PORT` (default 8082; `0` disables):
`POST /decide/<ctx>/(approve|reject)`, JSON body `{nonce, reason, approver}`. It calls the
existing `decide_pending(ctx, nonce, approved, reason, approver=f"{approver} (via slack)",
background=True)` and answers its `{status, text}` as JSON. Nothing else is served. The claim,
the nonce, the one-send rule and the n8n outcome post are the ones §T.119 built: the page and
the bridge are two doors to one decision path.

Who may knock: `network-policy.yaml` gains a rule admitting the `slack-bridge` namespace's
`app: slack-bridge` pod on `8082` and `15008`; a new `authorization-policy.yaml` (workload
selector `app: dispatcher`, ALLOW) admits port 8082 only from principal
`cluster.local/ns/slack-bridge/sa/slack-bridge`, and keeps every other port open with a
`notPorts: ["8082"]` rule (ALLOW semantics would otherwise refuse Grafana's plaintext webhook
and the gateway's HBONE to the sidecar). Both namespaces are ambient, so ztunnel enforces the
principal at L4 without a waypoint. The Service does not expose 8082: the bridge addresses the
pod through a second Service `dispatcher-decide` (port 8082 only), so the public HTTPRoute
cannot reach it even by mistake.

The pending finding the dispatcher posts gains `decision: {ctx, nonce, agent, task}`. The n8n
`agent-findings` workflow renders, when `decision` is present, a Block Kit message: the text
section as today plus an `actions` block with Approve (`primary`) and Reject (`danger`),
`action_id` `approve` / `reject`, value `d:<ctx>:<nonce>`. `text` stays as the fallback. The
`checksum/workflows` annotation is recomputed.

### 5. Security

- Tokens: the app-level token can only open a socket; the bot token can post, react and read
  the channels the app is in; neither can decide anything (a decision needs a click Slack
  attributes to the owner's user id). The kagent token never leaves the pod.
- Identity: the bridge's principal is admitted to the controller like the dispatcher's
  (§V.91 rule 2). Its sessions are its own; `ask-hk --as-serviceaccount slack-bridge/slack-bridge`
  continues them. The approver recorded for a dispatcher decision is `OWNER_EMAIL (via slack)`.
- The decide port is reachable only from the bridge pod (NetworkPolicy) and only as the
  bridge's principal (AuthorizationPolicy); the approvals page's 127.0.0.1 rule (§V.97) is
  untouched.
- Duplicates: a redelivered envelope (a crash between queueing and ack) re-runs the work; for a
  click the second run hits the nonce claim (dispatcher 409, or the bridge's own "already
  decided"); for a question it asks the agent twice in one session, which is visible and
  harmless.
- No rate limit: one owner, one connection. The Anthropic spend limit is the backstop.

### 6. Tests (`tests/slack_bridge/`, pytest, none extra)

- `test_websocket.py`: a fake RFC 6455 server on a local port (plain `ws://`): handshake,
  masked text frames, fragmented payload lengths (7-bit, 16-bit, 64-bit), ping → pong, close.
- `test_socket_mode.py`: a fake `apps.connections.open` + fake server that sends `hello`, an
  `events_api` envelope, an `interactive` envelope and `disconnect`: the bridge acks each
  envelope with its id, hands both to the handler, and reconnects after `disconnect`.
- `test_bridge.py`: with a fake A2A sender and a fake Slack: owner gating (ephemeral refusal,
  nothing sent); DM, mention and known-thread acceptance; `pick_agent`; a new thread → no
  context id, a follow-up → the same context id; the first reply carries the session line; a
  pause → pending block + buttons with `s:` value; approve → `tool_approval_response` for the
  registered ids on the registered task; a second click → "already decided"; `d:` value →
  POST to the dispatcher with `approver=OWNER_EMAIL` and the mapped reply text; errors and
  timeouts land in the thread.
- `test_manifests.py`: `checksum/code` matches the ConfigMap; the pod runs as `slack-bridge`
  with the projected token; the kagent controller NetworkPolicy admits `slack-bridge`; the
  dispatcher NetworkPolicy admits the bridge pod on 8082; the AuthorizationPolicy admits only
  the bridge principal on 8082 and keeps the other ports open; the `dispatcher-decide` Service
  exposes only 8082 and the public Service does not; the n8n workflow renders buttons when
  `decision` is present and none otherwise; `checksum/workflows` matches.
- `test_gen_configmap.py`: `--check` passes on the committed files and fails on a drifted copy.
- `tests/dispatch/`: `POST /decide/...` → `decide_pending` with `(via slack)`; the finding
  carries `decision` when a restart is registered; 404/409/400 mapping.

### 7. Rollout

1. Owner: Slack app changes (§2); run `scripts/provision-slack-bridge-vault.sh` (port-forward,
   OIDC login) with both tokens.
2. PR 1 (code + dispatcher + n8n + manifests, one PR: the bridge is useless without the door
   and the door is inert without the bridge). CI: the new suite, the dispatch suite, both
   `--check`s, kubeconform. The dispatcher pod rolls (checksum/code); n8n rolls
   (checksum/workflows, ~12 min); the bridge starts and logs `hello`.
3. Acceptance: DM `hello` → an answer with the session line; `k8s-reader: which pods restarted
   today` in `#oncall-alerts` with a mention → threaded answer; reply in the thread → same
   session id in the log; `restarter: restart homepage/<pod>` → pending block → Reject → "no
   restart"; replay a `leak` alert → n8n message with buttons → Approve → the dispatcher's
   outcome message, log `approved_by: <email> (via slack)`; a second account's click → ephemeral
   refusal.
4. SPEC: T120 (this), V98 (the bridge invariant: owner-only, own principal, decide port
   reachable only as the bridge). Memory note for the owner: a Slack app change (scopes) needs
   a reinstall, not a pod restart.
