# Kubernetes 1.34–1.36 Feature Adoption Implementation Plan

*Written 2026-09-25, the day after the cluster reached `v1.36.4+k3s1` (SPEC.md §T.21).*

## Overview

The walk from 1.33 to 1.36 made several features generally available that this cluster
can use directly. This plan adopts five of them, in five independent phases that can each
be shipped, verified and left alone before the next:

| Phase | Feature | Stage (verified in `pkg/features` @ v1.36.4) | What it buys here |
|---|---|---|---|
| 1 | Per-pod PSI metrics (`KubeletPSI`) | GA 1.36 | See which pods are starved of CPU/memory/IO, not just busy |
| 2 | In-place pod resize (`InPlacePodVerticalScaling`) | GA 1.35 | Right-size single-instance stateful pods without the restart that is an outage |
| 3 | Native admission policies (`MutatingAdmissionPolicy` GA 1.36; `ValidatingAdmissionPolicy` GA 1.30) | GA | Take policy enforcement off the Kyverno webhook, which is untested on 1.36 and fails *open* |
| 4 | Image volumes (`ImageVolume`) | GA 1.36 | Ship LLM weights as pinned OCI images instead of internet downloads into node-pinned PVCs |
| 5 | Structured authentication config (`StructuredAuthenticationConfiguration`) | GA 1.34 | `kubectl` login through the existing Dex, instead of the shared admin kubeconfig |

**Order rationale.** Phase 1 is risk-free and produces the data Phase 2 needs. Phase 2 fixes
two live hazards the research found. Phase 3 is the largest and has a deadline (Kyverno 1.20,
~2026-11, removes `kyverno.io/v1` — SPEC §T.80). Phase 4 depends on Phase 3's pull-secret
mutation covering image volumes. Phase 5 touches control-plane configuration and is
independent; it goes last but could move earlier.

### Decisions taken with the owner (2026-09-25)
- `generate-ecr-secret` is **deleted**, not migrated — the `ecr-auth` CronJob already does its job.
- Kyverno's end state is **reporting only** — kept for PolicyReports, out of the admission path.
- `kubectl` OIDC access is **pinned to the owner's GitHub ID**; no Dex-wide `orgs:` change.
- Model images are built by a **local script**, following `base-apps/kagent/build/build.sh`.

## Success Criteria
- [ ] A Grafana panel shows the pods most starved of CPU, memory and IO, and alerts fire for a starved pod and for a container near its memory limit.
- [ ] Prometheus and Vault can be resized in place without a restart, using a tested script and runbook.
- [ ] The pgvector `postgresql` Deployment can no longer run two Postgres processes on one data directory.
- [ ] All 8 remaining policies run natively in the API server. Enforce policies hold with Kyverno's admission controller scaled to 0. No ClusterPolicy remains, which resolves §T.80.
- [ ] `qwen` and `ollama` load weights from digest-pinned ECR images, with no PVC, no node pin and no startup download.
- [ ] `kubectl auth whoami` returns `oidc:arigsela` through Dex, and only that GitHub ID is accepted. The x509 admin kubeconfig still works as break-glass.
- [ ] After every phase, `scripts/hop-verify.sh gate` passes and 54/54 Argo apps are Synced+Healthy.

### Existing Patterns
- **GitOps first.** Every change is a PR; Argo auto-syncs. Terraform goes through Atlantis and is applied before merge (§V.73). Node-level files are the exception and get an installer script.
- **Generated artifacts are checked in with a `--check` mode** (agent-capability policy, TechDocs, OKF). The dashboard follows the same pattern.
- **Local build scripts for images:** `base-apps/kagent/build/build.sh` builds and pushes to ECR `852893458518.dkr.ecr.us-east-2.amazonaws.com`. ECR repos are not in Terraform.
- **Real-system drills beat static checks:** `tests/k3s-upgrade/` boots real k3s in Docker. Static tools missed things here: pluto cannot see CRD removals, kubeconform skips v1 MAPs, and kyverno CLI 1.18.2 misreports MAPs.

### Key Facts (research 2026-09-25)
- **PSI:** `container_pressure_{cpu,memory,io}_{waiting,stalled}_seconds_total` is already in Prometheus (labels `namespace/pod/container`). CPU waiting % today: backstage 23.45%, coroot-node-agent 5–10%.
- **Resize API behaviour** (verified with `--dry-run=server`):
  - Only resizes that keep the QoS class are allowed. Vault (BestEffort) cannot gain resources in place, and a limit cannot be removed.
  - The node's allocatable is enforced.
  - Memory-limit decreases are accepted, best-effort.
  - Nothing blocks `pods/resize`: Kyverno webhooks don't register it, and there is no LimitRange or ResourceQuota.
- **Resize candidates:**
  - **prometheus-0:** working set 2045Mi against a 2Gi limit (99.8%). Its GOMEMLIMIT is fixed at startup to 0.9 × limit.
  - **vault-0:** BestEffort. RSS stays ≤122Mi and the working-set growth is page cache.
  - **CNPG 1.30:** a resource change triggers a rolling update, which is an outage with one instance. In-place support is upstream PR cloudnative-pg#11116 (open).
  - **Deployments:** any template change is a rollout. No workload-controller in-place resize exists as of 1.36.
- **Native policies:**
  - **VAP:** 7 of 9 policies map to it. agent-capability rules 6–7 (delegation) work with `paramKind` Agent and `paramRef.selector: {}`; the draft was accepted server-side and passes all 9 real agents plus both escalation fixtures.
  - **MAP:** `inject-ecr-pull-secret` maps to one using ApplyConfiguration on the keyed list `PodSpec.imagePullSecrets`. How that merges on a real API server is **unverified**. *(Verified in 3D: it does not work, see Task 3.5.)*
  - **Not native:** `generate-ecr-secret` cannot be done natively.
  - **Today's weaknesses:** the Kyverno webhook fails open, and `disallow-latest-tag`'s `?*:?*` pattern does not catch `:latest`.
  - **MAP requirements:** `reinvocationPolicy` is required, and a MAP binding has no `validationActions`.
- **Image volumes:**
  - containerd 2.3 mounts images only, not OCI artifacts (containerd#11907, #11381), so each model is a `FROM scratch` image built for `--platform linux/amd64`.
  - `subPath` works.
  - The volume is resolved only when the pod is created.
  - Pull secrets come from the pod's `imagePullSecrets`.
  - Ollama v0.20.5 needs `OLLAMA_NOPRUNE=1` (startup prune at `server/routes.go:1764-1781`) and a writable `/root/.ollama` for its keypair.
  - llama.cpp mmaps GGUF files read-only.
  - ECR's maximum layer size is 52,000 MiB.
- **OIDC:**
  - The control node reaches Dex discovery and JWKS over hairpin NAT with a publicly trusted cert, so no `certificateAuthority` is needed.
  - **k3s stops passing `anonymous-auth=false` when `authentication-config` is set** (`pkg/daemons/control/server.go:221-225` @ v1.36.4), so the file must set `anonymous: {enabled: false}`.
  - An invalid file stops the API server at startup. Later edits hot-reload about every minute, and invalid edits are ignored and counted.
  - Dex `sub` for GitHub ID 2475907 is computed as `CgcyNDc1OTA3EgZnaXRodWI`. **Confirm it from a real token before pinning.**

### Dependencies
- Phase 1 → Phase 2: the pressure panels and alerts are how right-sizing is judged and verified.
- Task 3.5 → Phase 4: image-volume pulls from ECR need the pull-secret mutation to match `volumes[].image`. A stopgap is to extend the Kyverno precondition.
- Phase 5 depends on Dex reachability through the WAN allow-list, which is the same dependency Argo CD SSO already has.

## Architecture Decisions

### Decision 1: How native policies replace Kyverno policies
**Options considered:**
1. Big-bang swap: delete the ClusterPolicies, apply the native ones. Fastest, but one bad expression blocks legitimate changes cluster-wide.
2. Shadow first: native binding `[Warn, Audit]` alongside the Kyverno policy, compare verdicts, then switch the binding to `[Deny]` and delete the Kyverno policy.

**Chosen:** Option 2 for every validating policy. Mutation cannot run in shadow mode, so the MAP is bound to one test namespace first and widened after verification.

### Decision 2: Where native policies live
**Options considered:**
1. Inside `base-apps/kyverno-policies/`. No new app, but the name misleads and it ties the retirement of Kyverno policies to native ones.
2. A new `admission-policies` Argo app.

**Chosen:** Option 2. The objects are not Kyverno's, and the old app can be emptied and retired cleanly.

### Decision 3: Kyverno's end state
**Options considered:** remove entirely / keep for reporting / decide later.

**Chosen (owner):** keep for reporting only. Its reports controller already reports on native VAPs (`--validatingAdmissionPolicyReports=true`). With no ClusterPolicies, its resource webhooks carry nothing.

### Decision 4: How to use in-place resize under GitOps
**Options considered:**
1. Deploy VPA with `InPlaceOrRecreate` (GA in VPA 1.6). Automated, but any active mode fights git, and it adds a component.
2. VPA in recommendation-only mode. Advisory only, and memory recommendations are inflated by page cache.
3. A manual, scripted resize plus a git follow-up.

**Chosen:** Option 3. For `OnDelete` StatefulSets (Vault; Prometheus after Task 2.2), resize the running pod and then merge the same values, which gives a new revision with no restart. For Deployments, in-place resize is an emergency lever only, and the next git change rolls the pod. PromQL panels replace VPA recommendations for about six pods.

### Decision 5: Model packaging and build
**Options considered:** ORAS artifact (not mountable on containerd 2.3), `FROM scratch` image; built locally, by GitHub Actions, or by Argo Workflows.

**Chosen:** A `FROM scratch` image with one layer per file, pinned by digest, built by a local script (owner). Models change rarely, and the script mirrors `kagent/build/build.sh`.

### Decision 6: OIDC rollout on a single control plane
**Options considered:**
1. Add the full config and restart. A mistake leaves the API server down.
2. Two stages: restart with `anonymous: {enabled: false}` and `jwt: []`, which is explicitly valid, then add the Dex issuer by **hot reload**, where a bad edit is ignored instead of fatal.

**Chosen:** Option 2. The node files are kept in the repo (`node-config/k3s-control-01/`) and installed by a script that validates in a throwaway `rancher/k3s:v1.36.4-k3s1` container first. Access is pinned to the GitHub ID through `claimValidationRules` (owner).

#### Task 3.5: `inject-ecr-pull-secret` as a MAP
**Files:** `base-apps/admission-policies/inject-ecr-pull-secret.yaml`
**Steps:**
1. MAP on Pod CREATE. `matchConditions`: any container, initContainer **or `volumes[].image.reference`** contains `.dkr.ecr.`.
2. Mutation: `patchType: ApplyConfiguration` adding `{name: "ecr-registry"}` to `spec.imagePullSecrets` (a keyed list, so it merges by name). Set `reinvocationPolicy: Never`.
   - **Finding (3D, real 1.36 API server):** ApplyConfiguration is refused, because the list entries are `LocalObjectReference`, an atomic struct. With `failurePolicy: Ignore` that is a silent no-op. A JSONPatch whose value is a *list* of typed objects panics the API server's request handler, and the pod create fails whatever the failurePolicy. **Used instead:** a JSONPatch that adds an empty list if the field is missing, then appends one object unless it is already there.
3. Bind to a test namespace (`matchResources.namespaceSelector`), verify, widen to all non-system namespaces, then delete the Kyverno policy. Both mutate idempotently by name while both are active.

**Testing (real API server — harness plus on-cluster test namespace):**

## Risks and Mitigations
- **A native Deny policy blocks legitimate changes.** Mitigation: shadow bindings first, the real-API-server harness, `failurePolicy` chosen per policy, and instant rollback by editing the binding or `git revert`.
- **Delegation-VAP cost scales with the number of Agents.** Mitigation: 9 agents today; watch admission latency and `typeChecking`; fallback is a Kyverno ValidatingPolicy with `resource.Get`.
- **MAP merge semantics are unverified.** Mitigation: test-namespace binding first, plus explicit real-server tests (Task 3.5). *(Resolved in 3D: ApplyConfiguration cannot mutate the atomic entries, and a list-valued JSONPatch panics the API server; the policy uses the working JSONPatch form, and the harness guards both.)*
- **A bad authentication config prevents the API server from starting.** Mitigation: throwaway-container validation, a two-stage rollout, atomic writes, the break-glass kubeconfig, and hypervisor console access (`virsh console k3s-control-01` on 10.0.1.101).
- **A hot-reload-rejected file on disk becomes a startup failure at the next reboot or upgrade.** Mitigation: the installer only writes validated files; add a check of the reload-failure metric to the gate.
- **Planned restarts of Prometheus and Vault.** Mitigation: one short window each; Vault auto-unseals via KMS.
- **Model images fill node disk.** Mitigation: about 2GB today against 107GB+ free; image GC at 85%; the root-disk panel.
- **Dex availability becomes a login dependency.** Mitigation: the x509 admin kubeconfig remains, and nothing automated uses OIDC.
