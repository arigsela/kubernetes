# k3s upgrade runbook — v1.35.6+k3s1 → v1.36.4+k3s1

Operational companion to [`SPEC.md`](../../SPEC.md) (§T.21, rewritten under §T.78 on
2026-09-24). The spec holds the invariants and task graph; this holds the procedure, the
outage comms, and what to do when a hop goes wrong.

The July walk (1.33.5 → 1.34.9 → 1.35.6, §T.17-§T.19) is where most of the procedure below
was learned, usually the hard way. Its lessons are kept; its targets and component tables
are not.

## Target: `v1.36.4+k3s1`

**Unblocked.** 1.36 was capped by ingress-nginx, whose last release supports ≤1.35 (§R.13).
It was replaced by the Istio Gateway on 2026-07-31 (§T.43), which satisfies §V.46.

**Why this version.** `v1.36.4+k3s1` is on the k3s `stable` channel (since 2026-08-27). It
bundles Kubernetes 1.36.4, kine v0.16.4 on SQLite 3.53.4, containerd v2.3.4, flannel
v0.28.4 and local-path-provisioner v0.0.37 (§R.38). The release's Traefik warning does not
apply: Traefik is disabled here (`disable: traefik`).

**Why not 1.37.** It is out (1.37.0, 2026-08-26) but not on k3s `stable`, minors cannot be
skipped (§C), and almost nothing here states 1.37 support yet (§R.39). It is the next hop,
not this one. 1.35 itself is supported until 2027-02-28, so this is not a race.

**Removals.** Nothing Kubernetes removes or deprecates in 1.36 or 1.37 is used here: no
`gitRepo` volumes, no `Service.spec.externalIPs`, no ipvs kube-proxy, CoreDNS rather than
kube-dns, and every node is already on cgroup v2 (§R.40). The built-in API scan is clean
against 1.36 (`tests/k3s-upgrade/test_api_scan.py`).

Landed 2026-09-24 (§T.69-§T.72), all verified live:

| Component | Running | States 1.36? |
|---|---|---|
| cert-manager | v1.21.2 | yes (1.33-1.36) |
| CloudNativePG | 1.30.1 | yes (1.34-1.36) |
| Argo CD | v3.5.3 | yes (tested 1.33-1.36) |
| External Secrets | 2.8.0 | yes (1.35-1.36) |
| Istio | 1.30.3 | yes (1.32-1.36) |
| **Kyverno** | **v1.19.1** | **no — states 1.33-1.35** |
| Vault, Crossplane, system-upgrade-controller | — | no upper bound stated |

**Kyverno is the one accepted risk** (decision 2026-09-24, §T.72). Its chart does not
refuse 1.36 (§R.21), so this is "untested", not "unsupported". It is an admission webhook,
so the risk is concentrated in one place: if it misbehaves, pod creation is what breaks.
Three things bound that:

- the admission controller runs with `forceFailurePolicyIgnore=true`, so an unreachable
  webhook fails open rather than blocking every pod;
- `hop-verify.sh gate` now proves the admission path on every run — controllers
  available, every ClusterPolicy Ready, and a server-side dry-run pod create through the
  webhooks (`check_kyverno`);
- the emergency lever, if admission breaks anyway:
  ```bash
  kubectl delete validatingwebhookconfigurations,mutatingwebhookconfigurations \
    -l webhook.kyverno.io/managed-by=kyverno
  ```
  The admission controller recreates them on restart, so this is a stop-gap, not a fix.

## Before the window

1. **#586 merged and live** — `kubectl get cluster -n postgresql postgresql-cluster -o
   jsonpath='{.spec.smartShutdownTimeout}'` returns `30`. Without it the worker-01 hop
   costs donetick another ~3 minutes: its pooled connections hold smart shutdown open for
   the full 180s default (§T.69, §T.83).
2. **Announce** the window (table below). The control-plane hop takes `kubectl` and Argo
   away, so have anything you need for diagnosis in hand beforehand, and have console
   access to `k3s-control-01`.
3. **Fresh artifacts, off-cluster.** The gate refuses stale ones:
   ```bash
   scripts/k3s-backup.sh   --mode cold --dest ~/k3s-upgrade-artifacts   # on the node
   scripts/pg-backup.sh    --dest ~/k3s-upgrade-artifacts --all
   scripts/vault-backup.sh --dest ~/k3s-upgrade-artifacts --argo-app vault
   ```
4. **Gate** — a command, not a checklist (§T.29, §T.30):
   ```bash
   scripts/hop-verify.sh gate      # non-zero exit means do not hop
   ```
   It checks the three artifacts and their checksums, nodes, Argo drift (§V.47), CNPG,
   Vault, ESO, the Istio dataplane (§V.49), live CNI failures (§V.50/§V.51), the ingress
   Gateway, and Kyverno's admission path. Until 2026-09-24 it silently stopped after the
   Argo check whenever the cluster was clean (`set -e` plus a false test in a trailing
   note); if a run ends without a `GATE PASSED`/`GATE FAILED` line, treat it as failed.
5. **Pause auto-sync** for the window (§V.18, §V.30, §B.4):
   ```bash
   scripts/argo-sync-window.sh scope     # see what is in scope, change nothing
   scripts/argo-sync-window.sh pause     # master-app first, then every PVC-bearing app
   ```
   `system-upgrade-controller` carries no PVC, so it keeps syncing — the worker hop below
   depends on that.

## Hop 1 — control plane (manual)

Manual, never SUC (§V.17): SUC on the sole control-plane node can strand the cluster. Never
label `k3s-control-01` with `k3s-upgrade`.

```bash
# on k3s-control-01; note the epoch first, `watch` measures §V.9 from it
date +%s
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.36.4+k3s1 \
  INSTALL_K3S_EXEC="server --write-kubeconfig-mode=644" sh -
```

The installer **regenerates** `/etc/systemd/system/k3s.service` from `INSTALL_K3S_EXEC`
and ignores the existing `ExecStart`, so the flags must be re-supplied every time.
`/etc/rancher/k3s/config.yaml` (here, `disable: traefik`) is untouched. Diff the unit
against a backup afterwards; it costs nothing.

Then, **the moment k3s is back** — the istio-cni step below — then `watch`, then `gate`.

## Hop 2 — workers (system-upgrade-controller)

One PR, one line: `version:` in `base-apps/system-upgrade-controller/plan-agent.yaml`
`v1.35.6+k3s1` → `v1.36.4+k3s1`. Both workers already carry `k3s-upgrade=true`;
`concurrency: 1` takes them one at a time, `cordon: true`, no drain (local-path PVs are
node-pinned, so a drain could never reschedule them). Argo syncs it despite the pause
(see above). Watch the plan:

```bash
kubectl -n system-upgrade get plans,jobs -w
```

On **each** worker as it returns: the istio-cni step, then `watch`. After the second:
`gate`.

## The moment k3s returns on a node, before anything else

A k3s upgrade extracts into a new `/var/lib/rancher/k3s/data/<hash>/` and repoints
`data/current`. In July the istio-cni DaemonSet installed its binary under
`data/current/bin/`, which the kubelet had resolved **when the pod was created** — so after
the hop the pod kept writing into the old directory, `istio-cni` dangled, and every new pod
sandbox on the node failed (§B.7). On control-01 that took out CoreDNS, then Argo's
repo-server, then all 57 apps.

§T.46 has since moved istio-cni's `cniBinDir` to `/var/lib/rancher/k3s/data/cni`, the
stable directory containerd reads, which k3s does not rotate. That should make the problem
impossible, but **it has never been through a real hop**. So this hop tests it and keeps
the old remedy anyway:

```bash
# 1. evidence for §T.46 — does the plugin still resolve? (-L follows the link)
sudo ls -lL /var/lib/rancher/k3s/data/cni/istio-cni
# 2. the remedy, regardless of what 1 said
kubectl delete pod -n istio-system -l k8s-app=istio-cni-node \
  --field-selector spec.nodeName=<node>
```

Record step 1's result per node in §T.21. If it resolves on all three nodes, that is the
evidence to propose retiring the restart (an amendment to §V.50), not before.

Do not verify by exec'ing into the pod — that check passed in July while the node was
broken, for the same reason the DaemonSet never self-heals. Do not rely on DaemonSet
readiness either: all three pods were `Ready` for the entire outage.

Note that no namespace is enrolled in ambient any more (chores-tracker, the only ambient
workload, was removed), so istio-cni and ztunnel currently serve nothing while still
carrying this risk. Whether to keep the ambient dataplane at all is an open question, not a
blocker.

**If sandbox creation failed on a node at all, audit its IPAM afterwards** (§V.51). flannel
hands out the IP *before* the chained plugin runs, so every attempt that failed at the
istio-cni step leaked a reservation. Eighteen minutes of retries in July leaked 219 of
control-01's 254 addresses; the node then could not create **any** pod for fourteen hours.

```bash
# on the node — count reservations against reality
sudo ls /var/lib/cni/networks/cbr0/ | grep -c '^10\.'
```

Prune by keeping a file if **either** its IP is a live pod IP **or** its container id appears
in `k3s crictl pods -q` / `ps -aq`; delete only what matches neither. Tar the directory
first. Do not wipe it wholesale — live pods hold reservations in there and would collide.
If a classifier says nothing is live, distrust the classifier before the data: the first one
written in July ran under `sudo sh -c`, where `k3s` is not on `PATH`, and would have deleted
14 live reservations.

## After each hop

```bash
scripts/hop-verify.sh watch --since <epoch of k3s stop>   # measures the §V.9 window
scripts/hop-verify.sh gate                                 # includes the Kyverno checkpoint
```

Every node `Ready`, every Argo app `Synced+Healthy` (the gate names the one allowed
cascade), Vault unsealed, CNPG healthy. Only then does the next hop start. Kyverno's
checkpoint failing after a hop is the specific thing the §T.72 decision is watching for:
stop, use the emergency lever above if pods cannot be created, and do not continue.

## Barman restore, proven 2026-07-28 (§T.34)

The S3 backups had never been restored from. They have been:

```yaml
# scratch namespace, credentials copied from postgresql/postgresql-backup-credentials
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:16.4   # must match or exceed the source
  enablePDB: false                                     # a temp cluster must not block drains
  bootstrap:
    recovery: {source: pg-barman-source}
  externalClusters:
    - name: pg-barman-source
      barmanObjectStore:
        destinationPath: s3://mysql-backups-asela-cluster/postgresql/
        serverName: postgresql-cluster      # serverName is unset on the source, so it
        # ... s3Credentials as per the source cluster
```

Healthy in about two minutes. `serverName` is empty on the source cluster, so it defaults to
the cluster name — the recovery spec must state `postgresql-cluster` explicitly. The restored
cluster gains an empty `app` database the source does not have; that is CNPG's default
bootstrap database, not a discrepancy.

CNPG 1.30 still serves `barmanObjectStore`; 1.31 removes it (§R.41). Moving to the Barman
Cloud Plugin — and re-proving this restore on it — is §T.79, before any CNPG 1.31 bump.

## Rollback

k3s migrates the SQLite datastore one-way and does not support downgrade; 1.36.4 also moves
kine to v0.16.4. **The filesystem artifact is the only rollback**, which is why §V.16 refuses
to call an untested one a backup.

```bash
scripts/k3s-restore.sh --artifact <file> --expect-version v1.35.6+k3s1
```

It gates on the checksum, moves the existing tree aside rather than destroying evidence,
promotes the SQLite snapshot, and refuses to report success unless the API answers at the
expected version. Data-layer rollbacks are independent: the `pg_dumpall` and Vault
artifacts, plus barman in S3.

## Hard-won specifics

- **§B.7 / §B.8** — the istio-cni orphaning and the IPAM leak it causes. Handled above.
- **§B.1** — kine runs SQLite in WAL mode. Never archive a live `state.db` without its
  `-wal`/`-shm` siblings, or exclude all three and use `sqlite3 .backup`. A torn artifact
  checksums cleanly and cannot restore.
- **§B.2 / §B.4** — suspending an Argo app is not enough; `master-app` re-applies it from
  git mid-operation. Suspend **both** — `argo-sync-window.sh` does.
- **§B.3** — anything mounting a control-plane-pinned volume needs the
  `node-role.kubernetes.io/control-plane` toleration, or it sits `Pending` forever.
- **§B.5** — changing a CNPG cluster's affinity **restarts the primary**, whatever the docs'
  trigger list implies. (`smartShutdownTimeout` does not: it is read at shutdown time and is
  not part of the pod spec.)
- **§B.6** — confirm `status.sync.revision` equals the merged commit **before** re-enabling
  auto-sync, and repair `last-applied-configuration` after any out-of-band `kubectl patch`.
- **§B.13** — anything under `terraform/` is applied by Atlantis from the **open** PR.
  Merging before `atlantis/apply` is green strands the change with every check green.

## Verification tooling

`tests/k3s-upgrade/` is the oracle. The drills boot real k3s, PostgreSQL and Vault in
Docker, destroy them, and require the data back — that is what caught §B.1. CI runs them on
every PR via the `k3s-upgrade-scripts` job, including a run of the real gate against an
unreachable API, which must fail loudly rather than stop quietly.
