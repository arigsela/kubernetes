# k3s upgrade runbook — 1.33.5 → v1.35.6+k3s1

Operational companion to [`SPEC.md`](../../SPEC.md). The spec holds the invariants and task
graph; this holds the procedures, the outage comms, and what to do when a hop goes wrong.

Satisfies §T.39. §V.41 gates §T.17 on this existing, because §V.9 requires the outage window
to be *announced* and there was previously nothing to announce it from.

## Target: 1.35, not 1.36

The original target was `v1.36.2+k3s1`. An audit on 2026-07-28 (§R.13–§R.18) found four
components that cap at Kubernetes 1.35:

| Component | Version | Reaches 1.36? |
|---|---|---|
| **ingress-nginx** | v1.15.1 | **Never** — repo archived 2026-03-23, terminal release |
| CloudNativePG | 1.24.1 | No — 1.29.x supports ≤ 1.35 |
| external-secrets | v0.11.0 | No — even 2.7 supports ≤ 1.35 |
| Kyverno | v1.17.1 | No — v1.18 supports 1.33–1.35 |
| cert-manager | v1.20.2 | Yes, via v1.21 |
| Istio | 1.24.0 | Yes, via 1.30 |

Three of those may ship 1.36 support eventually. **ingress-nginx cannot** — the repository is
archived and `controller-v1.15.1` is the last release that will ever exist. Reaching 1.36
therefore requires migrating ingress onto Gateway API first (§T.43), which is a project in
its own right and out of scope here.

**1.35 is the destination.** It restores support (1.33 went EOL 2026-06-28) and buys roughly
seven months.

## Before any hop

Both relocations are already done — `vault-0` and `postgresql-cluster` now run on
`k3s-worker-01`, so a control-plane hop no longer takes secrets and databases with it.

Still outstanding, and all three gate §T.17:

1. **§T.42 — `ServerSideApply=true`.** Eight apps carry chronic large-CRD drift, which makes
   §V.5 (*every app Synced+Healthy*) unsatisfiable. It also prevents a repeat of §B.6.
2. **§T.18's PDB block.** The CNPG PDB reports `disruptionsAllowed: 0` and follows the
   primary — it now blocks draining `k3s-worker-01`. Mitigate at hop time by scaling to 2,
   setting `enablePDB: false`, or using `nodeMaintenanceWindow`.
3. **Component remediation**, re-scoped once the target became 1.35 (§R.20):

   | Component | Running | Needed for 1.35 |
   |---|---|---|
   | ingress-nginx | v1.15.1 | **nothing** — already 1.31–1.35 |
   | cert-manager | v1.20.2 | **nothing** — already 1.32–1.35 |
   | CNPG | **1.29.1** | **done** (§T.9) — five sequential steps, CVE fixed |
   | Istio | 1.24.0 | **deferred** (§V.49) — see below |
   | Kyverno | v1.17.1 | → v1.18.x (§T.44) — advised, not required |

   Worth knowing the distinction (§R.21): the charts' own `kubeVersion` constraints are
   permissive — kyverno declares `>=1.25.0-0`, istio and crossplane declare none — so
   nothing will *refuse* to install at 1.35. The published matrices are tested-version
   statements. "Out of matrix" here means untested, not blocked.

**Istio is deferred past the walk** (§V.49). It cannot be upgraded quickly: `istio-cni`
and `ztunnel` tolerate only one minor of skew from the control plane (§R.23), so 1.24 → 1.29
is five sequential steps of four components each, and every ztunnel step briefly disrupts
ambient traffic on the node. Istio 1.24 is *already* outside its tested range on 1.33
(§R.24) and working, and only two namespaces use ambient.

The risk profile differs from ESO and is worth stating plainly: `istio-cni` is a CNI plugin
chained into node networking, so a failure could break pod creation on a node rather than
merely degrade a feature. **Every hop must therefore check that `istio-cni-node` and
`ztunnel` DaemonSets are Ready on all nodes and that both ambient namespaces still route.**
Stop the walk if they degrade.

**ESO is deferred past the walk** (decision 2026-07-28, §V.48). It is not mechanically
required: v0.11.0 already runs two minors out of its matrix on 1.33 and resolves 40 of 43
ExternalSecrets fine. At 1.35 it would be roughly four out. The accepted risk is that
secret *refreshes* stop while existing Secret objects persist — a gradual degrade, not an
outage. §V.11's check at each hop is the early-warning signal, and §T.18 (the 1.34 hop) is
the first real test. If §V.11 fails there, stop before 1.35.

That decision is what turns this from a multi-week project into a short one: any ESO move
past 0.16.2 requires migrating 56 manifests plus a CRD storage-version rewrite, and there
is no cheaper partial.

## Outage comms

| Hop | Affected | Expected | Notes |
|---|---|---|---|
| control-plane (§T.17, §T.19) | API, Argo, `kubectl` | ~10–15 min | Apps keep serving; Vault and Postgres are on worker-01 |
| `k3s-worker-01` (§T.18) | Vault, Postgres, `n8n`, `chores_tracker` | ~10 min | The heavy one post-relocation |
| `k3s-worker-02` (§T.18) | coroot, grafana, openshell, n8n pod | ~10 min | Node is 83% full — watch disk |

Announce before a control-plane hop; the API being down means Argo and `kubectl` are too, so
anything you need for diagnosis must be in hand beforehand.

## What the §T.16 dry run established

Run 2026-07-28 on `k3s-worker-02`, with the Plan pinned to the version already running:

```
t+0s    upgrade job created and scheduled on the node
t+15s   node Ready,SchedulingDisabled  (cordon applied)
t+31s   job Complete, node Ready       (uncordon)
```

The node **never went NotReady**, all 21 workloads survived, and the other two nodes
were untouched. Node selection worked exactly as scoped — only worker-02, never the
control plane, and not worker-01 (unlabelled, since it hosts Vault and CNPG).

**What this does not tell us.** The job logged `Binary already been replaced` and exited
0 without restarting k3s, because the binary checksums matched. So the machinery is
proven end to end, but the NotReady window for a *real* hop remains unmeasured — the
worker figures in the table above are still estimates. The first genuine hop (§T.18)
is what will produce that number.

## Per-hop procedure

**Gate first**, and it is a command rather than a checklist (§T.29, §T.30):

```bash
scripts/hop-verify.sh gate            # non-zero exit means do not hop
```

It checks all three artifacts exist and their checksums verify, nodes Ready, no
*unexplained* Argo drift (§V.47 — diagnosed causes allowed by name, merely tolerated ones
warned about every run), CNPG healthy, Vault unsealed, ESO no worse than its known three
failures, the Istio ambient dataplane (§V.49), and ingress-nginx via helm-controller.
What it cannot check — the component matrix, the API scan, the restore drill — it prints
as explicit operator items rather than passing silently.

Pause auto-sync for the window (§V.18, §V.30, and §B.4's lesson that the parent undoes the
children):

```bash
scripts/argo-sync-window.sh scope     # see what is in scope, change nothing
scripts/argo-sync-window.sh pause     # master-app first, then every PVC-bearing app
# ... hop ...
scripts/hop-verify.sh watch --since <epoch of k3s stop>   # measures the §V.9 window
scripts/argo-sync-window.sh resume    # restores exactly the prior policy
```

The old enumerated list, for reference — §V.31 requires the full set, not a bare "gate":
§V.1 (verified k3s backup + restore drill), §V.2/§V.27 (component matrix, or a bounded
transient), §V.5, §V.6 (fresh pg dump), §V.10 (API scan), §V.11 (ESO healthy), §V.14, §V.28
(Vault backup).

```bash
# artifacts — all three, off-cluster
scripts/k3s-backup.sh   --mode cold --dest ~/k3s-upgrade-artifacts   # on the node
scripts/pg-backup.sh    --dest ~/k3s-upgrade-artifacts --all
scripts/vault-backup.sh --dest ~/k3s-upgrade-artifacts --argo-app vault
```

**Control plane** is manual, never SUC (§V.17) — SUC on a sole control-plane node can strand
the cluster. Have console access before starting.

**Workers** go through system-upgrade-controller, agents only (§T.14, §T.15). Never label
`k3s-control-01`.

**The moment k3s returns on a node, before anything else** — restart that node's istio-cni
pod (§V.50). This is not optional and it is not a health check:

```bash
kubectl delete pod -n istio-system -l k8s-app=istio-cni-node \
  --field-selector spec.nodeName=<node>
```

A k3s upgrade extracts into a new `/var/lib/rancher/k3s/data/<hash>/` and repoints the
`data/current` symlink. The istio-cni DaemonSet mounts `data/current/bin/` as a hostPath,
and the kubelet resolved that symlink **when the pod was created** — so the running pod
keeps writing into the *old* directory. It does reinstall its binary after k3s restarts;
it just reinstalls it somewhere nothing will look. `data/cni/istio-cni` is left dangling,
containerd reports `failed to find plugin "istio-cni"`, and every *new* pod sandbox on that
node fails. Existing pods keep running, which is what makes it easy to miss.

On control-01 that took out coredns, so cluster DNS went down, so Argo's repo-server
failed its liveness probe (its `/healthz?full=true` does a git lookup) and all 57 apps went
`Unknown`. Deleting the pod fixed it in about ten seconds. Cost: §V.9 was 27m27s against a
15-minute bound.

Do not verify this by exec'ing into the pod to test for the binary — that check passes
while the node is broken, for the same reason the DaemonSet never self-heals. Do not rely
on the §V.49 DaemonSet check either: all three pods were `Ready` for the entire outage.
`scripts/hop-verify.sh gate` now checks the symptom directly (§V.50).

**After each hop**: every node `Ready`, every Argo app `Synced+Healthy`, Vault unsealed and a
real secret readable, both databases serving. Only then does the next hop start.

## Barman restore, proven 2026-07-28 (§T.34)

The S3 backups had never been restored from. They have now:

```yaml
# scratch namespace, credentials copied from postgresql/postgresql-backup-credentials
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:16.4   # must match or exceed the source
  enablePDB: false                                     # a temp cluster must not block drains
  bootstrap:
    recovery: {source: pg-barman-source}
  externalClusters:
    - name: pg-barman-source
      barmanObjectStore:
        destinationPath: s3://mysql-backups-asela-cluster/postgresql/
        serverName: postgresql-cluster      # serverName is unset on the source, so it
        # ... s3Credentials as per the source cluster
```

Healthy in about two minutes. Verified against the live source: database sizes exact
(`n8n` 290MB, `chores_tracker` 8260kB), `chores_tracker` row counts 3/1/3/3 all
matching, `n8n.invalid_auth_token` 2/2. Torn down afterwards and the PV reclaimed.

Two things worth knowing next time. `serverName` is empty on the source cluster, so it
defaults to the cluster name — the recovery spec must state `postgresql-cluster`
explicitly. And the restored cluster gains an empty `app` database the source does not
have; that is CNPG's default bootstrap database, not a discrepancy.

## Rollback

k3s migrates the SQLite datastore one-way and does not support downgrade. **The filesystem
artifact is the only rollback**, which is why §V.16 refuses to call an untested one a backup.

```bash
scripts/k3s-restore.sh --artifact <file> --expect-version v1.34.9+k3s1
```

It gates on the checksum, moves the existing tree aside rather than destroying evidence,
promotes the SQLite snapshot, and refuses to report success unless the API answers at the
expected version.

Data-layer rollbacks are independent: retained PVs from the relocations sit `Released` on
`k3s-control-01`, plus the `pg_dumpall` and Vault artifacts, plus barman in S3 — though
barman's restore is still unproven (§T.34).

## Hard-won specifics

Seven bugs are recorded in §B. These are the ones that will bite again:

- **§B.7** — a k3s hop orphans any CNI binary under `data/current/bin/`, and the owning
  DaemonSet cannot heal itself because its hostPath was resolved at pod-create. Restart
  `istio-cni-node` on every node you hop, immediately. See the per-hop procedure above.
- **The installer rewrites the systemd unit.** `curl -sfL https://get.k3s.io | ... sh -`
  regenerates `/etc/systemd/system/k3s.service` from `INSTALL_K3S_EXEC`; it does not read
  your existing `ExecStart`. Re-supply the flags or lose them:
  `INSTALL_K3S_EXEC="server --write-kubeconfig-mode=644"`. Anything in
  `/etc/rancher/k3s/config.yaml` (here, `disable: traefik`) is safe — the installer does not
  touch it. Diff the unit against a backup afterwards; it costs nothing.

- **§B.1** — kine runs SQLite in WAL mode. Never archive a live `state.db` without its
  `-wal`/`-shm` siblings, or exclude all three and use `sqlite3 .backup`. A torn artifact
  checksums cleanly and cannot restore.
- **§B.2/§B.4** — suspending an Argo app is not enough. `master-app` re-applies it from git
  mid-operation. Suspend **both**.
- **§B.3** — anything mounting a control-plane-pinned volume needs the
  `node-role.kubernetes.io/control-plane` toleration, or it sits `Pending` forever.
- **§B.5** — changing a CNPG cluster's affinity **restarts the primary**, whatever the docs'
  trigger list implies. A restarted primary cannot schedule away from its own PV. Broaden,
  relocate, narrow (§V.43).
- **§B.6** — confirm `status.sync.revision` equals the merged commit **before** re-enabling
  auto-sync; Argo will sync a cached older revision. And repair
  `last-applied-configuration` after any out-of-band `kubectl patch`, or the next reconcile
  merges stale content back in.

Two of those six cost real downtime. Both were found by executing, not by review.

## Verification tooling

`tests/k3s-upgrade/` is the oracle. The drills boot real k3s, PostgreSQL and Vault in Docker,
destroy them, and require the data back — that is what caught §B.1. CI runs them on every PR
via the `k3s-upgrade-scripts` job.
