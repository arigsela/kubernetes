# Crossplane

**Status:** living. Reviewed 2026-09-30 against `base-apps/crossplane-*`, `base-apps/*-aws-infrastructure/`, `appsets/managed-apps/` and `terraform/roots/asela-cluster/iam.tf`. Includes the upgrade lessons from the v1.15 → v2 upgrade (2026-04-26/27).

## What it is
Crossplane provisions the AWS resources apps need (S3 buckets, IAM users, policies, access keys, one GitHub-OIDC role) as Kubernetes objects synced by Argo CD. It also carries a dormant self-service API, `XApplication`. Everything here belongs to eight Argo CD Applications, all **generated by the `managed-apps` ApplicationSet** (`base-apps/managed-apps.yaml`, one config per app in `appsets/managed-apps/`; runbook: `docs/managed-apps-appset.md`). None has a hand-written `base-apps/<app>.yaml`.

| Application | What it holds |
|---|---|
| `crossplane-system` | Crossplane core **2.2.1**. An umbrella Helm chart (`base-apps/crossplane-system/Chart.yaml` depends on `crossplane` 2.2.1 from `https://charts.crossplane.io/stable`), with resource requests/limits and metrics in `values.yaml`. |
| `crossplane-aws-provider` | Upbound `provider-family-aws`, `provider-aws-s3` and `provider-aws-iam`, all **v2.5.3**. The `default` ProviderConfig and the `aws-provider-runtime` DeploymentRuntimeConfig. |
| `crossplane-functions` | `function-python` v0.4.0, `function-extra-resources` v0.3.0. |
| `crossplane-compositions` | `XApplication` XRD (`platform.arigsela.com/v1alpha1`, namespaced), the `application` Composition, and an aggregated ClusterRole. |
| `loki-`, `argo-workflows-`, `jupyter-`, `agent-audit-aws-infrastructure` | The managed resources (table below). |

## Architecture & data flow
- **Sync waves in `crossplane-aws-provider`:** wave 0 is the family provider and the DeploymentRuntimeConfig, wave 1 the S3/IAM sub-providers, wave 2 the ProviderConfig (after the providers have installed their CRDs).
- **Provider resources:** every provider references `runtimeConfigRef: aws-provider-runtime`, which requests 100m CPU / 256Mi and allows up to 1 CPU / 1Gi. Without a CPU guarantee, the v2.5.x S3 provider's startup CRD cache sync can time out and crash-loop.
- **Credentials:** the ProviderConfig `default` (`aws.upbound.io/v1beta1`) reads key `creds` of Secret `crossplane-system/aws-secret`, an AWS INI `[default]` profile for IAM user `crossplane-admin`. That user and its policy (`s3:*` and `iam:*` on `*`) are Terraform, in `terraform/roots/asela-cluster/iam.tf`. See Gotchas for where the Secret comes from.
- **API version:** all managed resources use the legacy **cluster-scoped** `*.aws.upbound.io/v1beta1` APIs, plus `v1beta2` for Loki's lifecycle rule. They are selected by `providerConfigRef: default`. Migrating to the namespaced v2 MR APIs was explicitly out of scope for the v2 upgrade and hasn't been done.
- **Access keys** are minted by an `AccessKey` MR with `writeConnectionSecretToRef` into the consumer's namespace. Connection-secret keys:
  - `username` is the **access key ID**;
  - `attribute.secret` is the secret key;
  - there is **no `attribute.id`**.

### The dormant `XApplication` path
`crossplane-compositions` defines `XApplication` ("I have an image, run it"). A single-step `function-python` Composition emits:
- a Deployment, Service and Ingress;
- when `dbNeeded`, a CNPG `Cluster` plus a SecretStore / PushSecret / ExternalSecret round-trip through Vault;
- when `s3Needed`, a PushSecret / ExternalSecret pair. The bucket MRs themselves were meant to be scaffolder-emitted raw manifests.

The aggregated ClusterRole `crossplane:compositions:application` lets the Crossplane ServiceAccount manage Ingresses, CNPG Clusters and ESO objects.

It has been **dormant since the Backstage New App template (`templates/new-app/`) replaced it**. Nothing in git creates an `XApplication`. It is also **stale** (SPEC §T.76, verified 2026-09-30): the composition still emits an nginx `Ingress` (`ingressClassName: nginx`) with `cert-manager.io/cluster-issuer: letsencrypt-prod`. Neither nginx nor that issuer exists any more, so a new `XApplication` would get no route and no certificate. Its PushSecrets are `external-secrets.io/v1alpha1`.

**Render tests:** `tests/composition/`. `render.sh <case>` runs `crossplane render` for `xr-minimal`, `xr-with-db` and `xr-with-s3` and diffs against the `expected-*.yaml` goldens. They need the `crossplane` CLI, Docker and `yq` v4, and they **aren't run in CI** (no workflow references them). The goldens also contain the stale Ingress.

## Gotchas & tribal knowledge
- **`crossplane-system/aws-secret` is not produced by anything in git.** `provider-config.yaml` says Terraform creates it, but commit `37ed838` (2026-03-29) removed both the `aws_iam_access_key` and the `kubernetes_secret` from `iam.tf`. What's left says "Credentials are managed externally and stored in Vault". Yet no ExternalSecret in `crossplane-system` produces `aws-secret`. The Secret that Crossplane depends on is therefore hand-made (or an out-of-git leftover), and rotating it is a manual procedure: new `crossplane-admin` key, rewrite `creds`, revoke the old key. Its live state and origin weren't verified here. Every Crossplane-managed AWS resource stops reconciling if it goes stale.
- **`base-apps/crossplane-system/secret-store.yaml` is dead YAML.** The directory is a Helm chart (Argo auto-detects `Chart.yaml`), and Helm renders only `templates/`. A file at the chart root is never applied. No ExternalSecret in `crossplane-system` references it anyway.
- **No managed resource sets `deletionPolicy: Orphan`.** All use the default `Delete`, so removing an MR manifest from git makes Argo prune it (`prune: true`) and Crossplane deletes the real AWS object: bucket, IAM user, access key (breaking the consumer at once). The ApplicationSet guards only against the *generator* going empty (`preserveResourcesOnDeletion: true`, `applicationsSync: create-update`, no resources-finalizer). It does nothing for a deleted file. If you need a resource to outlive its manifest, set `deletionPolicy: Orphan` on it and sync that change first.
- **`function-extra-resources` has no consumer.** It was installed for the `XSmokeTestApp` composition, which was deleted on 2026-07-20; its header comment says so. Removing the Function is a manifest change that hasn't been made.
- **The argo-workflows AccessKey comment is wrong.** `base-apps/argo-workflows-aws-infrastructure/access-key.yaml` says `attribute.id` holds the key ID. The jupyter and agent-audit comments (checked against the live `argo-workflows-s3-creds`) and the Argo chart config use `username`.
- **An AccessKey aimed at a namespace that doesn't exist fails to reconcile** and turns its whole app Degraded. That happened when the agent-audit-web key shipped before its namespace (PR #635). Ship the key with, or after, the namespace.
- **Selectors and labels can cross-match.** `userSelector` / `policyArnSelector` match on labels. agent-audit-web's resources deliberately use `app: agent-audit-web`, never `app: agent-audit`, so the exporter's selectors don't pick them up. Reference by name when in doubt.
- **S3 tag values allow only letters, digits, spaces and `+ - = . _ : / @`.** Parentheses or commas fail with `InvalidTag` and leave the bucket `Ready=False`.
- **Lifecycle `filter` and `expiration` are single-element lists in the v2 provider schema, not objects.** Objects reconcile but break Argo's structured-merge diff ("expected list, got map").

## Runbook
### Symptom: MRs `SYNCED=False` / `READY=False`, or every AWS resource stuck
- **Check:**
  ```bash
  kubectl get providers.pkg.crossplane.io,providerrevisions.pkg.crossplane.io
  kubectl get managed          # or: kubectl get buckets.s3.aws.upbound.io,users.iam.aws.upbound.io,accesskeys.iam.aws.upbound.io,policies.iam.aws.upbound.io,userpolicyattachments.iam.aws.upbound.io
  kubectl describe <kind>.<group> <name>        # the Synced/Ready condition message carries the AWS error
  kubectl -n crossplane-system get pods
  ```
- **Fix:**
  - **All resources failing with auth errors:** the `aws-secret` credential is stale or revoked. See the first Gotcha, and rotate it by hand.
  - **One resource failing:** read its condition (`InvalidTag`, `AccessDenied`, a name collision, a selector matching nothing).
  - **A provider pod crash-looping at startup:** check `aws-provider-runtime`'s resources.

### Symptom: a consumer's credential Secret is missing
- **Check:** `kubectl get accesskeys.iam.aws.upbound.io <name> -o yaml`. Look at `writeConnectionSecretToRef` and whether the target namespace exists.
- **Fix:** create the namespace (via its app). The provider writes the Secret on its next reconcile. Consumers read `username` / `attribute.secret`.

### Upgrading Crossplane or the AWS providers
Order: **providers first, core second**, as separate PRs, verified between them (§V.8).

1. **Providers (`base-apps/crossplane-aws-provider/provider.yaml`).** Bump `provider-family-aws`, `provider-aws-s3` and `provider-aws-iam` **together, to the same version**. The family provider is declared explicitly on purpose. Left implicit, it stayed at the previously auto-installed `v2.3.0` when the sub-providers moved to `v2.5.3`. Both sub-provider revisions then sat at `HEALTHY=Unknown` with repeated `ResolveDependencies` warnings.
   - **Verify:** `kubectl get providers.pkg.crossplane.io` shows every provider `INSTALLED=True` and `HEALTHY=True` at the new tag. `kubectl get providerrevisions.pkg.crossplane.io` shows the newest revision `Active`. All MRs stay `SYNCED=True` and `READY=True` with no new Warning events.
2. **Core chart (`base-apps/crossplane-system/Chart.yaml`).**
   - Resolve the target with `helm repo update crossplane && helm search repo crossplane/crossplane --versions`.
   - Confirm that every key in `values.yaml` still exists: `helm show values crossplane/crossplane --version <v> | grep -E '^(resourcesCrossplane|resourcesRBACManager|metrics):'`.
   - Render old vs new: `helm dependency update && helm template . -f values.yaml` on the branch and on `main`, then diff. Don't commit the `charts/` directory this creates (it isn't gitignored).
3. **Before merging the core bump, pre-check two CRD hazards that blocked the v2 upgrade:**
   - **Conversion webhooks and stored status.** The first core sync blocked Argo CD's whole cluster cache: `conversion webhook for s3.aws.upbound.io/v1beta1, Kind=BucketLifecycleConfiguration failed: json: cannot unmarshal string into ... objectSizeGreaterThan of type float64`. The old provider had written `""` into `status.atProvider`, the new schema typed it `float64`, and Argo couldn't list the kind, so it couldn't apply the fix: a circular block. This repo uses `BucketLifecycleConfiguration` at **both** `v1beta1` (jupyter, agent-audit) and `v1beta2` (loki), so the conversion path is live. The hotfix, out-of-band (confirm with the owner first):
     ```bash
     kubectl get crd bucketlifecycleconfigurations.s3.aws.upbound.io -o jsonpath='{.spec.conversion}' > /tmp/conv.json
     kubectl patch crd bucketlifecycleconfigurations.s3.aws.upbound.io --type=merge -p '{"spec":{"conversion":{"strategy":"None","webhook":null}}}'
     kubectl patch bucketlifecycleconfiguration.s3.aws.upbound.io <name> --subresource=status --type=merge -p '{"status":{"atProvider":null}}'
     kubectl patch crd bucketlifecycleconfigurations.s3.aws.upbound.io --type=merge -p "{\"spec\":{\"conversion\":$(cat /tmp/conv.json)}}"
     ```
     Then refresh the Argo apps. Watch for any field that narrowed type (string → number) between provider versions.
   - **`status.storedVersions` on Crossplane's own CRDs.** v2.2.1's init container crash-looped with `environmentconfigs.apiextensions.crossplane.io is invalid: status.storedVersions[0]: Invalid value: "v1alpha1": missing from spec.versions`. Kubernetes won't drop a stored version. Audit before bumping:
     ```bash
     kubectl get crd -o custom-columns=NAME:.metadata.name,STORED:.status.storedVersions | grep crossplane.io
     ```
     For a version the new core no longer serves (candidates at the time: `EnvironmentConfig`, `Usage`, `Lock`): if **no objects of that kind exist**, delete the CRD and the new init recreates it. If objects exist, you need a real storage migration first.
4. **If the rollout stalls, scale the old ReplicaSet to zero.** While the new core pod was looping in init, the old ReplicaSet stayed at 1 replica, and its init kept re-creating the old CRD, undoing the fix. `kubectl -n crossplane-system scale rs <old-rs> --replicas=0`, then repeat the CRD delete.
5. **Verify:** the `crossplane` Deployment's image matches the new `appVersion`, the `crossplane` and `crossplane-rbac-manager` pods are Ready, and the provider/MR checks from step 1 are unchanged. If Argo then reports `field not declared in schema`, that's the stale-schema issue in `base-apps/argo-cd/runbook.md`.
6. **Rollback:** `git revert` the offending PR. Trigger a revert if any of these happen:
   - an MR goes `READY=False` for more than 5 min;
   - a provider isn't `HEALTHY` within 10 min;
   - `crossplane` crash-loops;
   - Argo shows a Helm render error for `crossplane-system`.

During the 2026-04 upgrade, the data plane (every MR) stayed `SYNCED=True` and `READY=True` throughout all four problems above. The trouble is confined to the package-manager/CRD layer. That means a stuck upgrade is urgent for GitOps, not for the buckets.

**Functions:** bump the tag in `base-apps/crossplane-functions/function-python.yaml` **and** `tests/composition/functions.yaml` together, then run `tests/composition/render.sh` for each case locally.
