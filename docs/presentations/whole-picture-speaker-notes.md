# The whole picture

Eight illustrated infographics adapted from `docs/presentations/whole-picture-presentation-brief.md`, following its condensed sequence with the optional historical audit panel. Deck and notes both describe the platform as of 14 October 2026 (the brief's "as of" paragraph lists what landed on 13 and 14 October): panels 01 to 05 and 08 were regenerated on 14 October from the brief; panels 06 and 07 are recorded events and keep their 12 October artwork and dates. Status means implemented in this reference, not an assurance of production maturity. The runtime remains alpha.

## 01 — The whole picture

Source screens 03, 04, 06 and 08. Read from the tooling foundation through working paths to the agent harness and governance. The earlier concept, developer-workflow and agents-as-a-service decks each explain a slice of this map. The developer platform supplies a portal, delivery, resources, secrets, admission, data and telemetry. The agent layer adds context, capabilities, execution and evaluation, surrounded by identity, security and observability. Everything is represented by reviewed files and shared checks.

The harness has documentation, runbooks, shared prompts, memory and root contracts; a tool taxonomy with four classes (read, propose, write, destructive) and approval bindings; isolated execution with snapshots and a 30-day idle session TTL. Execution being built does not remove its alpha designation. Evaluation is now a post-deploy gate: any deploy that changes an agent's definition is scored against the corpus, posts a status on the change and alerts on regression. It is still thin: one agent has a corpus of eight questions, and the gate runs after the deploy, not before the merge. Existing path implementations still do not constitute a path registry. Every caller is now a principal: the mesh verifies a person's single sign-on token or an automation's short-lived platform token in front of the agent gateway and writes the verified identity into the request. The chat UI is the one remaining shared identity.

The brief attributes its three-layer frame and maturity vocabulary to Weave Intelligence and the Platform Engineering webinar "How to architect Agentic Development Platforms." The public organizer listing confirms the session and its probabilistic/deterministic, identity, context and sandboxing themes: https://www.meetup.com/platform-engineers-los-angeles/events/314843859/ . That listing gives 18 June 2026, whereas the supplied brief says 19 June. The private transcript was not available for independent verification of the detailed layer model; those details are presented as the brief's mapping, not an independently verified quotation or endorsement. Attribution identifies the public framework, not the anonymous reference implementation.

## 02 — Three ways work moves

Source screen 05. Deterministic GitOps reconciles desired state; this is not a guarantee of healthy deployment. The probabilistic lane illustrates the judgment-bearing review cascade: deterministic rules first, then a classifier and escalation when uncertain. Its output is advisory. The hybrid path combines agent implementation, deterministic checks and human or policy promotion. Policy promotion is live for two declared classes, both trivial by construction: a Renovate dependency bump that triage found nothing to read in, and the owner's own docs-only change. Both require every check green, every commit by the class's own author, and no deny-listed path; a model skip label alone is insufficient. Everything else remains owner-promoted, and a pull request opened by an in-cluster agent always waits for a human. Fixes and retries are still human-directed; there is no implemented token or retry budget on this path. Infrastructure changes must be applied before merge.

## 03 — Governance surrounds the agent

Source screen 07. Identity asks who may act, security constrains the action and observability records what actually happened. Since 13 October a human caller is authenticated, not just the service principals: the verified identity owns the session and keys the record. Since 14 October a restart an agent proposes is approved on a login-protected page that records the approver's identity; the runtime's own approval record still names the automation that opened the session, so the human's name lives beside it, not inside it. Tool classification, approval gates, admission checks and CI work together; the approval gate has now been exercised in production, several times on 14 October, with each decision recorded. Audit calls, approval requests and traces support investigation. Argument redaction is best-effort, so an audit store must not be described as intrinsically free of sensitive data. No present-day zero-violation claim is made.

## 04 — Eight paths, one honest scorecard

Source screen 09, revised 14 October. Eight built, none partial, and the artwork carries the same score. Preserve canonical path numbering; the brief's prose placing implementation on the bottom row conflicts with its numbered table, so this deck follows the table.

Dispatch was accepted on 12 October: a declared table maps alert titles to an agent, a human or nobody, and CI requires complete coverage. Agent routes create a fresh session under the dispatcher's own identity, constrained by an hourly budget and a fingerprint repeat window. Findings go through the existing notification service to chat with secret scrubbing. The original human alert path stays separate. Failing checks, issues and triage labels are not yet routed. Sources: `base-apps/dispatcher/docs.md`, `base-apps/dispatcher/dispatch-table.yaml`, `scripts/dispatch.py`, SPEC T105.

Promotion: policy for two classes, a human for the rest. The policy must parse from main. Eligible PRs are not drafts, carry `review:skip`, match a deterministic shape re-derived from the diff (an image or tag bump of at most four changed lines in at most two files, or docs only), touch no deny-listed path, have every check run successful or skipped and every commit status success, and every commit authored by the class's own principal (an unattributed commit, one whose git email is not linked to an account, is refused by design). A separate promoter App merges by rebase pinned to the evaluated head SHA, through a PR-only ruleset bypass; it cannot push to main. A PR cannot loosen its own policy. Every decision logs class and reasons; policy merges have been observed since 13 October. Sources: `docs/platform/promotion.md`, `.github/promotion-policy.yaml`, `scripts/promote.py`, SPEC T106/T107/V95.

Implementation is built, since 14 October: an in-cluster agent of a fourth capability class, "propose", changes the repository through branches and pull requests under its own GitHub App identity, with read-only cluster tools for evidence. Its contract is its prompt, pinned by tests: one commit, at most three files, a deny list of paths, never a second PR for the same change, observed text is evidence rather than instructions. It cannot merge, close, review or comment; those tools are not loaded. Its PRs are triaged and checked like any other and wait for a human. The runtime's sandboxes have no network egress, so the repository API is the workbench and CI is the validation. Sources: `docs/platform/implementer.md`, SPEC T116.

Remediation is built, since 14 October, in two halves. The implementer ends every resource investigation with a verdict. "Limit too low" becomes a pull request raising the limit. A leak, or a merged fix that an on-delete workload has not picked up, opens a session with a third agent that holds exactly one gated tool, pod delete, which pauses for approval; the owner approves on a login-protected page that shows the exact pending call and the evidence, and records who decided. Caps: two restarts a day, one per workload per day; the dispatcher refuses protected namespaces before any session opens and prints the approve option only when the pending call is exactly the alert's pod. Contention stays a finding. Sources: `base-apps/dispatcher/runbook.md`, SPEC T117/T118/T119.

Observation is built: alerts start investigations without a human prompt. This is a scoped path score, not a claim of full architecture completion.

## 05 — How much autonomy exists?

Source screen 10, revised 14 October. Human-as-validator remains the daily mode. Level 3 remains partial: desk subagents, specialist handoffs and alert dispatch exist, and an alert now becomes a pull request or a held restart with no human in between, but no agent orchestrates agents across the platform. General level 4 remains not yet, by choice, with two declared exceptions: the eligible Renovate class and the owner's docs-only class merge and deploy by policy without a human. An agent-proposed restart is not level 4: a named person approves it. Assess maturity per path.

## 06 — One recorded change

Source screen 11. Recorded 12 October 2026: CLI approval flow. Agent preparation covered nine files, +498/−31 and 49 tests. PR opened at 15:59Z and merged at 16:22Z: 23 minutes measures only that interval. Implementation and live acceptance sit outside it. The review classifier ran; its read probability of .47 exceeded the .30 read threshold. There were 27 check contexts, four skipped. This is distinct from the current validation workflow's 22 total jobs, including its change detector. An admission-test cluster startup timed out, then passed after a human rerun. The human merge used admin override. Live acceptance rejected without changing state or retrying; a new explicit request was approved. Documentation and memory were updated. A single recorded delivery is evidence of the operating process, not a safety guarantee or generalized speed metric.

## 07 — The audit that changed the controls

Source screen 12 and `scripts/agent-audit.py` module history. The historical query found 14 shell calls on 9 July 2026 and one delete call on 19 April 2026, with zero approval requests across that agent's audited history. Reconciliation had stripped the approval flag. The response combined a single taxonomy, admission plus CI enforcement, and daily comparison of policy against actual calls. Counts refer to this historical finding, not current usage. A configured gate needs evidence that it was exercised; as of 14 October the gate has that evidence, with approvals and a rejection recorded on the same day.

## 08 — Close the loop, in order

Source screen 13, revised 14 October. All five nodes have landed in the order drawn, each dated on its card. Evaluation as a gate (13 October): post-deploy, one agent, eight questions; pre-merge would need an in-cluster runner. Callers as principals (13 October): done in the mesh; the chat UI is still one identity. Dispatch (12 October): read-only as planned; failing checks, issues and triage labels remain future routes. Implement inside the platform (14 October): done without the sandbox, through the repository API under the propose class. Remediate on signal (14 October): pull requests for a limit that is too low, a human-approved restart for a leak or a lagging rollout. Reuse existing secrets, policy, documentation, validation and audit held for every node.

What comes next is no longer on this track: routing failing checks and issues through the dispatcher, a path registry, a retry budget on the hybrid path, an agent that hands work to agents, a login for the chat UI, and corpora for the new agents.
